      WebWatch guide

      A local monitor for public webpages

      Use these sections when you need a quick reminder. WebWatch saves settings and page history in its local database.

      Add and manage pages

      Add a public HTTP or HTTPS page with a display name and a 15-minute to 24-hour check interval. Adding saves the page; choose Check now to create its first successful baseline. Use each row’s edit and settings controls to change its name, interval, render mode, selectors, keyword alerts, numeric tracking, watched regions, or visibility. Hidden pages remain monitored; local demos are excluded from scheduled checks.

      Watchlist, checks, and automatic monitoring

      Search or filter the watchlist, open History, or run Check now. Check all shows progress and per-page results. Automatic monitoring runs only while the app is open; each page uses its own interval. The setting below it is only the default for newly added pages. Next scheduler pass is an estimate and may be delayed if the app is stopped or the computer sleeps.

      Statuses, serious events, and troubleshooting

      Baseline saved, No change, and Content changed describe successful checks. Network, DNS, timeout, HTTP denial, rate limit, CAPTCHA/challenge, blocked, or selector errors are failed attempts; they do not replace the last good snapshot or count as content changes. Fix the page URL or selector, check connectivity and the site’s availability, then retry later. WebWatch does not log in or bypass site restrictions. Expand a serious event to read its details; opening it marks it read. Browser notifications are optional.

      Troubleshooting Common Errors

      Main document exceeds the per-resource limit

      If a check reports The main document exceeded this website's 512 KiB per-resource limit., increase the limit for that page:

      1. Open the page’s More menu, then open Settings.
      2. Find Main document limit (KiB) and increase it from 512 to 1024 KiB first. Save settings, then choose Check now.
      3. If the page still exceeds the limit, increase it further as needed, up to 4096 KiB, save, and check again. Larger documents use more resources, so raise this limit only when needed.

      This setting applies only to the page’s main HTML document. Each subresource has its own 512 KiB limit, and all resources together remain limited to 8 MiB and 100 requests. Increasing the main-document limit does not change those other limits.

      Webpage exceeded the render timeout

      An error such as The webpage exceeded the 35-second render limit. is about the global rendering deadline, not the per-page document-size setting in More > Settings. This version defaults to 60 seconds and supports 35 to 120 seconds through the WEBWATCH_RENDER_TIMEOUT_SECONDS service environment variable. The number in the error reflects the active deadline.

      1. In the Render Dashboard, open the test service and go to Environment.
      2. Add or update WEBWATCH_RENDER_TIMEOUT_SECONDS with the value 120, then save the change and allow the service to redeploy.
      3. Confirm the deployed code reads this variable, then retry with Check now. The timeout takes effect when the application starts with the setting.

      A longer limit gives a slow page more time, but does not guarantee it can be rendered. Some pages may still time out because they are slow, complex, or difficult to load.

      Screenshot unavailable

      This warning means WebWatch could not save a screenshot for that check. The page text check may still have succeeded. Choose Check now to try again. If it keeps happening, note the page URL (remove any private query values before sharing), the check time, the exact screenshot warning, and whether the check status and saved text indicate success. The warning alone does not identify a specific cause.

      Retry a failed check and read its result

      1. Choose Check now on the affected page, or use Check All to retry the watchlist.
      2. Read the latest attempt and error shown on the page row. The Persistent check queue also shows recent attempts and their errors.
      3. A render, timeout, or size-limit error means the check could not complete; it does not by itself mean the website is unreachable. A DNS or network failure can create a suspected unreachable event after a previously successful check, but one failure does not confirm the site is down. Content changed means a successful check found different content; open History to review or compare saved versions.
      History, comparisons, and exports

      History can show all successful checks or only content changes. Open an entry for text changes and screenshots, then compare any two saved versions. Export history as JSON or readable HTML; the HTML page can be printed or saved as PDF from your browser. Snapshots and comparisons remain available according to the current database retention settings.

      Email, webhooks, and delivery queue

      Email needs a recipient plus SMTP host and sender settings on the server. Webhooks need an HTTPS destination; Telegram can also use a chat ID, while Discord uses its webhook URL. Save settings, then send a test. Webhook secrets stay hidden in the browser. Delivery options include a daily UTC digest and optional AI summaries. The queue shows recent check attempts, retries, and errors; alert delivery failures are recorded without exposing destination secrets. Content alerts are limited to one per page per hour.

      Keywords, numbers, and RSS

      Keyword-only alerts watch for configured phrases in page text. Numeric tracking uses a page’s configured selector and stores successful numeric observations; open its chart to review values over time. Each monitored page has an RSS feed for saved content versions.

      Browser extension

      Use Quick Add on the page currently open in your browser, review the detected URL and proposed name, then choose Review in WebWatch to submit it in the app. Manage monitored pages opens the WebWatch watchlist. The extension does not submit until you review and confirm.

      AI summaries and setup

      AI summaries are optional and use a provider key configured on the server; page excerpts are sent only when summaries are enabled and the provider is configured. Without a key, WebWatch uses its tested fallback summary. Live provider-generated summaries have not been verified in this environment because no key is configured.

      WebWatch checks public pages using its protected rendering path. It preserves your last successful snapshot when a check fails and does not bypass access controls.
